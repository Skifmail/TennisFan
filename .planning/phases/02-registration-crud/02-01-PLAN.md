# Plan 02-01: Phase 2 — Регистрация клуба и базовые CRUD

**Phase:** 2 (Регистрация и базовые CRUD)  
**Цель:** Регистрация клуба (3 шага, с trial без оплаты), API клуба, публичная страница `/club/{slug}`, инвайт-ссылки и флоу вступления, добавление игрока админом (по email и CSV), блок «Входящие приглашения» в ЛК игрока.

**Источники:** PROJECT.md, ROADMAP Phase 2, club_dev_spec.docx §1–2.  
**Зависимости:** Phase 1 выполнена (модели clubs, Tournament.club).

---

## Prerequisites

- Приложение `apps.clubs` с моделями Club, ClubSubscription, ClubMember, ClubInviteLink и др.
- В Phase 2 оплату подписки клуба **не** подключаем — только **trial 14 дней** для тарифа Старт (активация без платежа). Оплата — Phase 5.
- Данные шага 1 и 2 регистрации до активации хранить в **сессии** (или в одном объекте после шага 3).

## Task 1: Маршрутизация и структура apps.clubs

- Создать `apps/clubs/urls.py`: пока пустой `urlpatterns` или только префикс для последующих путей.
- В `config/urls.py` добавить `path("club/", include("apps.clubs.urls"))` (или `path("club/", ...)` с префиксом без trailing slash — по спецификации `/club/{slug}`, значит префикс `club/`).
- Создать `apps/clubs/views.py` (пустой или с заглушками под задачи 2–7).
- При необходимости создать `apps/clubs/forms.py` для форм регистрации и инвайтов.

**Проверка:** Запуск приложения без ошибок, переход на `/club/` не падает (404 или пустая страница допустимы).

## Task 2: Логика регистрации клуба (trial)

- **Сервис/хелпер создания клуба с trial:** функция `create_club_with_trial(data: dict, user)`:
  - Валидация данных клуба (name, slug, city, address, email, phone, admin_name и т.д.); slug уникален.
  - Создание `Club` (status=ACTIVE или TRIAL по решению; при trial — `status=TRIAL`, `trial_ends_at=now()+14d`).
  - Создание `ClubSubscription`: plan=START, period=yearly (или из данных), price=0 для trial, started_at=now(), ends_at=now()+14d, status=active.
  - Создание `ClubMember`: user=текущий пользователь, role=admin, status=active, joined_at=now().
  - Создание `ClubRating` для этого member (points=0), если рейтинг создаётся при вступлении (опционально в Phase 2).
  - Возврат созданного клуба (или slug для редиректа).
- Вызывать эту логику из view шага 3 после валидации данных из сессии.

## Task 3: Вьюхи трёх шагов регистрации клуба

- **Стартовый экран выбора типа аккаунта.** По спецификации: URL `/register`, при выборе «Я представляю клуб» → переход на `/register/club/step-1`. Реализация: либо отдельная страница выбора (например в `users` или `core`), либо страница в `clubs`: `club/register/` с двумя карточками («Игрок» → `reverse('register')`, «Клуб» → `club/register/step-1/`). Альтернатива: на существующей странице `/users/register/` добавить второй вариант и редирект на `club/register/step-1/`.
- **Шаг 1 — данные клуба.** URL: `club/register/step-1/`. GET: форма (название, город, адрес, логотип, email, телефон, ФИО ответственного, описание). POST: валидация, сохранение в `request.session['club_registration_step1']`, редирект на `club/register/step-2/`. Логин обязателен (декоратор `@login_required`).
- **Шаг 2 — выбор тарифа.** URL: `club/register/step-2/`. GET: отобразить три тарифа (Старт/Базовый/Про), переключатель помесячно/ежегодно (цены можно захардкодить или вынести в настройки). POST: сохранить в сессию выбранный plan, period; редирект на `club/register/step-3/`.
- **Шаг 3 — активация (trial).** URL: `club/register/step-3/`. GET: сводка из сессии (данные шага 1 + тариф). Для тарифа Старт — кнопка «Активировать бесплатно 14 дней» (trial). POST: вызвать `create_club_with_trial(session_data, request.user)`, очистить сессию, редирект на `/club/dashboard/` (или на публичную страницу клуба) с сообщением об успехе. Оплату в Phase 2 не делаем — только trial.

**Проверка:** Авторизованный пользователь может пройти все три шага и оказаться админом созданного клуба; клуб и подписка в БД в ожидаемом состоянии.

## Task 4: API клуба (получение по slug, обновление профиля)

- **Получение клуба по slug:** view или API endpoint `club/<slug>/` (GET). Возврат: JSON с полями клуба (name, slug, city, address, logo url, email, phone, description, is_public, status) для публичного отображения или для редактирования. Проверка: для публичной страницы — клуб должен быть is_public и (по спецификации) тариф Базовый или Про для публичной страницы; на тарифе Старт — 404 или редирект. В Phase 2 можно упростить: отдавать клуб по slug только если is_public.
- **Обновление профиля клуба:** endpoint или view `club/<slug>/edit/` (POST/PATCH). Доступ: только пользователь с ролью admin (или manager, если решим давать редактирование). Поля: name, city, address, logo, email, phone, admin_name, description, is_public. Валидация и сохранение в БД.

Реализация: либо отдельные view с JSON response, либо одна view с разбором по методу/параметру. Формат (JSON vs HTML form) зафиксировать в плане: для публичной страницы — HTML; для «редактирование профиля» из панели клуба — можно HTML form (Phase 4) или уже JSON API.

**Проверка:** GET по slug возвращает данные клуба; обновление профиля доступно только админу клуба и сохраняет изменения.

## Task 5: Публичная страница клуба

- **View:** `club_public_detail(request, slug)`. Получить клуб по slug; если нет или не is_public — 404. По спецификации: на тарифах Базовый/Про — показывать страницу; на Старт — 404 или редирект. Рендер шаблона с блоками: шапка (логотип, название, город, контакты), описание, список предстоящих турниров клуба (Tournament.objects.filter(club=club, status=...)), кнопка «Вступить в клуб» (если не авторизован → ссылка на login с next; если авторизован и уже в клубе — «Вы уже в этом клубе»; иначе — ссылка на join или форма).
- **URL:** `club/<slug>/` (без `join` в этом же task).
- **Шаблон:** создать `templates/clubs/club_public_detail.html` (или в корне templates по принятой в проекте схеме).

**Проверка:** Переход на `/club/<slug>/` для клуба с is_public=True отдаёт страницу; для несуществующего или is_public=False — 404.

## Task 6: Инвайт-ссылки — генерация и флоу вступления

- **Генерация ссылки:** view или API для админа/менеджера клуба: параметры expires_at (опционально), max_uses (опционально). Создать запись `ClubInviteLink`: club, token=secrets.token_urlsafe(32)[:64], created_by=request.user, expires_at, max_uses, use_count=0, is_active=True. Ответ: URL вида `request.build_absolute_uri(reverse('clubs:join', kwargs={'slug': club.slug}) + '?token=' + link.token)` или отдать token для копирования.
- **Страница вступления по токену:** URL `club/<slug>/join/` (GET и POST). GET с query `token=...`: валидация токена (существует, is_active, не истёк, лимит не исчерпан); если пользователь не авторизован — редирект на login с next обратно на join; если уже в клубе — сообщение «Вы уже в этом клубе»; иначе — форма/кнопка «Вступить в клуб». POST: создать `ClubMember` (user=request.user, club, role=player, status=active, joined_at=now()), инкремент `ClubInviteLink.use_count`, редирект в ЛК или на страницу клуба с сообщением.
- **Валидации:** токен не найден / неактивен / истёк / лимит исчерпан — отдельные сообщения об ошибке (страница ошибки или флеш-сообщение).

**Проверка:** Админ создаёт инвайт, переходит по ссылке под другим пользователем (или тем же), нажимает «Вступить» — в клубе появляется участник, use_count увеличился.

## Task 7: Добавление игрока админом (по email, приглашение)

- **Поиск пользователя по email:** API или view (GET/POST) для админа клуба: параметр email. Поиск `User.objects.filter(email=email).first()`. Если найден — вернуть данные (id, email, для отображения ФИО/аватар если есть); если не найден — сообщение «Пользователь не найден».
- **Отправка приглашения:** создание `ClubMember` с status=invited, invited_by=request.user (и опционально отправка письма «Вас пригласили в клуб X» со ссылкой на ЛК или на инвайт). В Phase 2 достаточно создать запись invited; отправку email можно заглушить или реализовать простым письмом (шаблон и send_mail).
- **Импорт CSV:** форма загрузки файла; парсинг CSV (например по строкам, колонка email или одна колонка). Для каждого email: поиск пользователя; если есть — создать ClubMember status=invited (или отправить письмо); если нет — занести в список «не найден» и не создавать или отправить письмо-приглашение на регистрацию (по спецификации). Ограничение: не создавать дубликаты (club + user unique). Вывод результата: «Добавлено N приглашений, не найдено: …».

Эндпоинты можно разместить в панели клуба (Phase 4) или уже сделать отдельные URL в Phase 2 (например `club/dashboard/players/invite/` — заглушка под будущий dashboard). Для плана достаточно описать логику и вызов из view.

**Проверка:** Админ клуба по email находит пользователя и создаёт приглашение; в списке приглашённых появляется запись со статусом invited.

## Task 8: Блок «Входящие приглашения» в ЛК игрока

- **Данные:** для текущего пользователя — список `ClubMember.objects.filter(user=request.user, status=invited).select_related('club')`.
- **Отображение:** в ЛК пользователя (в `users` или в общем шаблоне ЛК) добавить блок «Входящие приглашения»: для каждого приглашения — название клуба, кнопки «Принять» / «Отклонить».
- **Принять:** POST (или GET с подтверждением) на endpoint вида `club/invitations/<id>/accept/`. Обновить ClubMember: status=active, joined_at=now(); редирект с сообщением.
- **Отклонить:** POST на `club/invitations/<id>/decline/`. Обновить ClubMember: status=removed (или оставить invited и трактовать как «отклонено» — по модели лучше removed для единообразия). Редирект с сообщением.

Интеграция в ЛК: определить место в шаблоне (например в `users` profile или отдельная страница «Приглашения»). URL в `apps.clubs.urls` или в `apps.users.urls` — по архитектуре проекта.

**Проверка:** Пользователь с приглашением видит блок; «Принять» переводит в активного участника клуба; «Отклонить» убирает приглашение из списка.

## Task 9: Интеграция «Выбор типа аккаунта» на странице регистрации

- На странице регистрации (`/users/register/` или корневой `/register/`) добавить выбор: «Я игрок» (текущий флоу) / «Я представляю теннисный клуб» (редирект на `club/register/step-1/`). Если текущая регистрация только для игроков — перед формой регистрации показать два варианта; для клуба редирект на шаг 1 (при этом пользователь должен быть авторизован для создания клуба — иначе сначала регистрация/логин как игрок, затем «представляю клуб» может вести в личный кабинет с пунктом «Создать клуб» или сразу на club/register/step-1 с требованием логина). Спецификация: «Если не авторизован → /login?redirect=...». Значит для шага 1 клуба пользователь уже должен быть залогинен; «Я представляю клуб» тогда показываем только залогиненным, иначе — «Войдите или зарегистрируйтесь, чтобы создать клуб» с кнопкой входа.

**Проверка:** Залогиненный пользователь с главной/регистрации может выбрать «Представляю клуб» и попасть на шаг 1; незалогиненный видит предложение войти.

## Task 10: Финальная проверка и ограничения по тарифу

- Проверить ограничение: публичная страница клуба на тарифе Старт — не показывать (404 или редирект). Проверка в `club_public_detail`: у клуба взять текущую активную подписку (ClubSubscription, status=active, последняя по ends_at); если plan=START — вернуть 404 или страницу «Публичная страница недоступна на тарифе Старт».
- Лимиты тарифов (макс. игроков, макс. турниров) в Phase 2 можно не проверять (Phase 4); зафиксировать в плане, что проверка лимитов — Phase 4.
- `python manage.py check` без ошибок; ручной проход флоу: выбор «Клуб» → шаги 1–2–3 (trial) → публичная страница (если переключить тариф на Базовый вручную в админке) → инвайт → вступление по ссылке → приглашение по email → блок «Входящие приглашения» (принять/отклонить).
