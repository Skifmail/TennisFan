# Plan 05-01: Phase 5 — Финансы

**Phase:** 5 (Финансы)  
**Цель:** Оплата подписки клуба платформе (тарифы Старт/Базовый/Про), подключение платёжного аккаунта клуба (ЮKassa), оплата членского взноса игроком через аккаунт клуба, webhook и return_url для фиксации оплат, мониторинг (таблица оплат и ручная отметка уже есть в Phase 4).

**Источники:** PROJECT.md §5, ROADMAP Phase 5.  
**Зависимости:** Phase 1–4 выполнены (модели, ЛК игрока, панель клуба, настройка взносов и ручная отметка).

---

## Prerequisites

- **Подписка клуба:** оплата идёт на счёт платформы (существующие `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` в settings). После успешной оплаты создаётся/продлевается `ClubSubscription`, при необходимости закрывается предыдущая подписка (status=cancelled или expired).
- **Членский взнос:** оплата идёт на счёт клуба. В `ClubMembershipFee` уже есть поля `payment_provider`, `payment_shop_id`, `payment_api_key`. Secret Key хранить зашифрованно (Fernet из `cryptography` с ключом из settings). Для создания платежа использовать API ЮKassa с учётными данными клуба; в metadata передавать `club_id`, `fee_id`, `member_id`, `period_label` для однозначной привязки при return и webhook.
- **Webhook ЮKassa:** один endpoint на платформе (например `POST /payments/club-fee-webhook/`), в теле запроса — данные платежа с metadata; по metadata создаём `ClubFeePayment` и отвечаем 200. Идентификация магазина по metadata (club_id/fee_id), проверка подписи/секрета при необходимости (документация ЮKassa).
- Stripe в Phase 5 можно не реализовывать (только ЮKassa); при необходимости заглушка «Скоро» в форме настроек.

## Task 1: Хранение Secret Key клуба (шифрование)

- Добавить в `config/settings.py` опциональную настройку `CLUB_PAYMENT_ENCRYPTION_KEY` (строка, 32 байта base64 для Fernet или сгенерировать из `SECRET_KEY`). Если пусто — не сохранять API key в БД (только ввод для проверки и создание платежа в рамках сессии не хранить).
- В `apps/clubs` ввести утилиту шифрования (например `apps/clubs/payment_utils.py`): `encrypt_secret(plain: str) -> str`, `decrypt_secret(encrypted: str) -> str`. Использовать `cryptography.fernet.Fernet`. При отсутствии ключа — не шифровать, только логировать предупреждение и сохранять как есть (для dev) или не сохранять.
- В модели `ClubMembershipFee` поле `payment_api_key` хранит зашифрованную строку. При отображении в форме настроек — показывать маску (например «••••••••») и отдельное поле «Новый Secret Key» (при заполнении — перезаписать зашифрованным). При создании платежа — расшифровать и использовать.

**Проверка:** Сохранённый API key не отображается в открытом виде; при создании платежа ключ корректно расшифровывается.

## Task 2: Расширение формы настроек взноса и создание платежа с учётными данными клуба

- В форме настроек взноса (Phase 4) добавить поля: `payment_provider` (choice: ЮKassa / Stripe-заглушка), `payment_shop_id`, поле «Secret Key» (optional, не показывать сохранённое значение, при вводе — сохранять зашифрованным). Валидация: при включённой онлайн-оплате (is_active и выбран провайдер) — shop_id обязателен; Secret Key обязателен при первом сохранении или при смене (если не маска).
- В `apps/payments/yookassa_client.py` (или в `apps/clubs`) добавить функцию `create_payment_with_credentials(shop_id: str, secret_key: str, amount: str, return_url: str, description: str, metadata: dict, customer_email: str | None = None) -> tuple[str, str]`. Логика как в существующей `create_payment`, но auth=(shop_id, secret_key) и без чтения из settings. Использовать при инициации оплаты взноса от имени клуба.
- Аналогично: `get_payment_status_with_credentials(payment_id: str, shop_id: str, secret_key: str) -> str | None` для проверки статуса после return (и при необходимости в webhook).

**Проверка:** Админ клуба вводит Shop ID и Secret Key ЮKassa, сохраняет; при создании платежа взноса используются эти данные.

## Task 3: Оплата подписки клуба платформе

- **Выбор тарифа и периода:** страница «Продлить подписку» или «Оформить подписку» (доступна админу клуба из раздела «Подписка»). URL: `club/<slug>/subscription/pay/` (GET — форма выбора плана и периода; POST — инициация платежа). Данные: план (START/BASIC/PRO), период (monthly/yearly). Цены брать из констант (как в Phase 2 PLAN_PRICES) или из настроек.
- **Создание платежа:** использовать существующую `create_payment` из `apps/payments/yookassa_client` (платформенные credentials). Параметры: amount (из выбранного плана/периода), return_url=`request.build_absolute_uri(reverse('clubs:subscription_return'))`, description=f"Подписка клуба {club.name}, тариф {plan}", metadata={club_id, plan, period, subscription_type: 'club'}. Сохранить в сессии или во временной модели `payment_id` и `club_id` для обработки return.
- **Return URL:** view `club/subscription/return/` (GET или POST — по документации ЮKassa return). По `payment_id` из query или из сессии проверить статус через `get_payment_status`. При status=succeeded: вычислить started_at/ends_at по выбранному плану и периоду, создать новую `ClubSubscription` (club, plan, period, price, started_at, ends_at, status=active, payment_ref=payment_id); предыдущую активную подписку перевести в expired или оставить как есть (по бизнес-логике — одна активная на клуб). Редирект на страницу подписки клуба с сообщением об успехе.
- **Хранение контекста оплаты:** чтобы на return знать план/период/сумму, сохранять в сессии (session['club_subscription_pending'] = {payment_id, club_id, plan, period, amount}) при редиректе на ЮKassa; на return по payment_id достать из сессии и создать подписку. Альтернатива: модель `ClubSubscriptionPaymentPending` (payment_id, club_id, plan, period, amount, created_at) — предпочтительно для надёжности (сессия может истечь).

**Проверка:** Админ выбирает тариф и период, переходит на оплату ЮKassa, после успешной оплаты возвращается на сайт — подписка создана/продлена, отображается на странице подписки.

## Task 4: Оплата членского взноса игроком (инициация и return)

- **Кнопка «Оплатить» в ЛК игрока:** в разделе «Членский взнос» (`club/my/fees/`) при fee_status unpaid или expiring_soon показывать кнопку «Оплатить». По нажатию — GET `club/my/fees/pay/` или POST на ту же страницу с действием «pay».
- **View инициации:** проверка: у клуба активная настройка взноса с заполненными payment_shop_id и payment_api_key (расшифрованным). Вычислить period_label для текущего периода (как в services.get_current_period_label). Создать платёж через `create_payment_with_credentials(fee.payment_shop_id, decrypted_secret, amount, return_url, description, metadata)`. metadata: club_id, fee_id, member_id, period_label. return_url: `request.build_absolute_uri(reverse('clubs:my_fees_return'))` с query-параметром payment_id (или передать в return_url как путь с id). Сохранить в сессии или в таблице ожидающих платежей: payment_id, member_id, fee_id, period_label, amount.
- **Return view:** `club/my/fees/return/` (GET). Из request.GET получить payment_id. По payment_id и сессии/таблице определить member, fee, period_label. Вызвать `get_payment_status_with_credentials(payment_id, fee.payment_shop_id, decrypted_key)`. При succeeded — создать запись `ClubFeePayment` (club, member, fee, amount, period_label, paid_at=now(), method=online, payment_ref=payment_id). Редирект на `club/my/fees/` с сообщением «Оплата прошла успешно».

**Проверка:** Игрок в разделе «Членский взнос» нажимает «Оплатить», переходит на форму ЮKassa (счёт клуба), после оплаты возвращается — в истории появилась запись об оплате, статус «оплачен».

## Task 5: Webhook для оплаты взноса (ЮKassa)

- В документации ЮKassa: уведомления (webhook) при смене статуса платежа приходят на URL, указанный в настройках магазина. Платформа предоставляет один endpoint: например `POST /payments/club-fee-webhook/` (в приложении `payments` или `clubs`). В настройках каждого магазина клуба в ЛК ЮKassa указывается этот URL.
- **Обработка запроса:** в теле приходит JSON с полем `object` (объект платежа): `id`, `status`, `metadata`. По metadata (club_id, fee_id, member_id, period_label) найти клуб, настройку взноса, участника. Проверить status == 'succeeded'. Если запись `ClubFeePayment` с таким payment_ref уже есть — не создавать дубликат (идемпотентность). Иначе создать `ClubFeePayment`. Ответить HTTP 200.
- **Безопасность:** проверить, что запрос от ЮKassa (по возможности проверка IP или подпись, см. документацию ЮKassa). При ошибке (нет metadata, не найден клуб) — логировать и ответить 200, чтобы ЮKassa не повторял запрос бесконечно.
- Сохранение payment_id при инициации: чтобы на return не полагаться только на сессию, можно сохранять в модель `ClubFeePaymentPending` (payment_id, club_id, fee_id, member_id, period_label, amount, created_at). Тогда на return и в webhook по payment_id находим запись и создаём ClubFeePayment один раз (с проверкой дубликата по payment_ref).

**Проверка:** После оплаты взноса webhook от ЮKassa обработан, в БД создана запись ClubFeePayment (если не была создана уже на return).

## Task 6: Модель ожидающих платежей (опционально, для надёжности)

- Создать модель `ClubFeePaymentPending` в `apps/clubs/models.py`: payment_id (CharField, unique), club (FK), fee (FK), member (FK), period_label, amount, created_at. При инициации платежа взноса — создавать запись. На return и в webhook — искать по payment_id, создавать ClubFeePayment, помечать Pending как обработанный (удалить или флаг processed) во избежание повторной обработки.
- Альтернатива: без модели, только сессия на return и webhook по metadata. Риск: при истечении сессии return не сможет сопоставить payment_id с member; webhook остаётся основным способом фиксации. Рекомендуется минимальная модель Pending для связи payment_id → member/fee/period.

**Проверка:** При повторном приходе webhook или двойном return дубликат ClubFeePayment не создаётся.
