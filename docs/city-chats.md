# Городские чаты

## Поведение

- `/chats/` — свои комнаты, непрочитанные и поиск населённых пунктов.
- Вступление явное и бесплатное. Город профиля не ограничивает выбор.
- Комната однозначно связана с `core.City` (название, регион и тип поселения).
- История доступна только активным участникам. Запрет писать не запрещает читать.
- Текст до 2000 символов, не чаще одного нового сообщения за 2 секунды на аккаунт.
- Повторный UUID отправки не создаёт дубль даже после обрыва ответа.
- Автор может редактировать сообщение 15 минут и удалять своё сообщение.
- Модератор комнаты (`ChatMembership.is_moderator`) или сотрудник удаляет нарушения и запрещает писать на сутки. Снять запрет можно в Django Admin.
- Жалобы рассматриваются в Django Admin; правила закрепляются в настройках комнаты.
- Уведомления об ответах приходят в существующую ленту сайта и отключаются отдельно в каждой комнате. Рассылки каждого сообщения, Telegram-уведомлений, файлов и личных диалогов нет.
- Удаление очищает текст. Удаление аккаунта оставляет сообщения с обезличенным автором; комнату города нельзя удалить удалением записи справочника.

## Надёжность и безопасность

HTTP-команды используют текущую Django-сессию и CSRF. WebSocket проверяет Origin по `ALLOWED_HOSTS`, актуальный аккаунт и участие при подключении, каждом событии и heartbeat. Не используйте `ALLOWED_HOSTS=*` в production. Все пользовательские строки вставляются в DOM через `textContent`.

WebSocket передаёт только сигнал изменений. Сам текст читается через защищённый HTTP-интерфейс. Сохранение сообщения и запись `ChatEvent` происходят одной транзакцией; публикация в Redis — только после commit. Redis не является хранилищем переписки. При недоступности Redis журнал восстанавливается клиентом через heartbeat (25 секунд), при переподключении — сразу. Журнал пока сохраняется без очистки; при введении retention понадобится протокол истёкшего курсора.

Блокировка комнаты сериализует изменения и порядок курсоров в PostgreSQL. SQLite подходит для разработки, но не даёт эквивалентной защиты конкурентных записей. Production требует PostgreSQL.

## Запуск

1. Установить зависимости из `requirements.lock` с проверкой хешей.
2. Применить миграции: `venv/bin/python manage.py migrate`.
3. Собрать статику: `venv/bin/python manage.py collectstatic --noinput`.
4. Запустить Redis и задать `CHAT_REDIS_URL` одинаковым для HTTP и ASGI процессов.
5. Оставить текущий Gunicorn для HTTP; запустить Daphne с `config.asgi:application` для `/ws/chats/`.

В `docker-compose.dokploy.yml` добавлены сервисы `chat` и `chat_redis`. Traefik направляет `/ws/chats/` на порт 8001, остальные пути остаются у текущего web-сервиса. Используется существующий образ приложения; `chat` переопределяет ENTRYPOINT и не запускает повторные миграции или cron. Web выполняет миграции под PostgreSQL advisory-блокировкой до запуска HTTP. Chat и cron зависят от успешной readiness-пробы web и не стартуют до завершения миграций. Статика собирается внутри образа, общий том static_data больше не используется (старый том не удалять). Подробнее: `docs/dokploy-runbook.md`.

В обычном `docker-compose.yml` сервисы добавлены, но внешний reverse proxy управляется отдельно. Для nginx в существующем TLS server-блоке нужен маршрут:

```nginx
location /ws/chats/ {
    proxy_pass http://chat:8001;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 75s;
}
```

`Procfile` — альтернативная схема: публичный web-процесс Daphne обслуживает HTTP и WebSocket вместе. Для ASGI задайте `CONN_MAX_AGE=0`. Прокси должен поддерживать Upgrade. `--proxy-headers` допустим только за доверенным прокси, прямой доступ к ASGI-порту не публикуется.

Для разработки: Redis на localhost, `DEBUG=True`, `CHAT_REDIS_URL=redis://127.0.0.1:6379/0`, затем `venv/bin/daphne -b 127.0.0.1 -p 8000 config.asgi:application`. Обслуживание статики — через локальный прокси или предварительный collectstatic/WhiteNoise; Daphne сам не заменяет Django runserver.

## Проверки

`TELEGRAM_ENABLED=False venv/bin/pytest tests/unit/chat/ tests/integration/chat/`

Проверяются правила текста, участие в чужом городе, повторы, изоляция комнат, история и прочтение, жалобы, модерация, CSRF, повреждённые запросы, доставка двум WebSocket-клиентам и закрытие после выхода. Транспортные unit/integration тесты используют InMemoryChannelLayer, не пригодный для production. Redis и PostgreSQL требуют отдельной инфраструктурной проверки перед rollout.

После деплоя проверить под двумя аккаунтами в разных браузерах: вступление, мгновенную доставку, переподключение, правки/удаления старых сообщений и запрет после выхода. Проверить HTTP 101 на публичном `/ws/chats/<room_id>/`, а не только открытие страницы. Наличие конфигурации не означает, что production уже обновлён.

### Локальная браузерная приёмка

Для повторения нужны отдельная PostgreSQL-база с именем `*_smoke` на localhost, отдельный Redis и два процесса Daphne (порты 18765 и 18766). Все команды выполняются с `DJANGO_SETTINGS_MODULE=tests.support.chat_browser_settings` и переменными подключения **к тестовой**, а не рабочей базе.

После миграций выполнить collectstatic **до запуска процессов Daphne**: WhiteNoise индексирует файлы при старте. Подготовить сессии:

```bash
venv/bin/python manage.py shell -c 'from pathlib import Path; from tests.support.chat_browser_seed import create_smoke_sessions; create_smoke_sessions(Path("/tmp/city-chat-sessions.json"))'
```

Затем запустить два Daphne, задать `CHAT_E2E_URL=http://127.0.0.1:18765`, `CHAT_E2E_SECOND_URL=http://127.0.0.1:18766`, `CHAT_E2E_SESSION_FILE=/tmp/city-chat-sessions.json` и выполнить `venv/bin/pytest tests/e2e/chat/`. Если Chromium не установлен Playwright, указать `CHAT_BROWSER_EXECUTABLE`. Требуются dev-зависимости из `requirements-dev.txt`. Файл сессий приватный, его нельзя коммитить или публиковать.

Строгая проверка новых модулей: `venv/bin/mypy --config-file=mypy-chat.ini apps/chat config/asgi.py tests/unit/chat tests/integration/chat tests/e2e/chat`. В конфигурации включены strict и Django typing plugin; старые модули не включаются в область проверки.

## Результаты проверки реализации

Локально выполнены: 44 теста нового модуля на PostgreSQL, покрытие серверного модуля 96%; отдельная браузерная проверка двух аккаунтов через два процесса Daphne и настоящий Redis; mypy strict, black, ruff, stylelint и синтаксическая проверка JavaScript. Проверены конкурентные повторы, общий лимит аккаунта между городами и одновременные перекрёстные ответы с уведомлениями без взаимной блокировки FK.

Общий прогон существующего проекта: 961 passed, 4 failed, 3 skipped и 138 успешных subtests. Четыре падения воспроизведены на чистом снимке HEAD до изменений: три теста доступа в старый закрытый Telegram-чат и один тест CSS спаррингов. Они не исправлялись в рамках городского чата.

`manage.py check` и проверка отсутствующих миграций **для chat** проходят. Глобальный `makemigrations --check --dry-run` выявляет ранее существовавшие расхождения полей `subscriptions.UserSubscription.end_date` и `users.PlayerSportProfile.entry_level_set`; те же результаты подтверждены на исходном HEAD. Не генерировать и не применять эти несвязанные миграции автоматически при выпуске чата.

Рабочая SQLite-база и секреты не изменялись. Проверка публичного сайта и production-rollout в эту работу не входили: конфигурация подготовлена, но рабочий сайт ещё не обновлён.

## Светлый интерфейс чата

Раздел использует отдельную оболочку `templates/chat/base.html`: глобальная зелёно-золотая тема, общий footer и плавающий виджет поддержки сюда не подключаются. Остальные страницы платформы не изменены. Оформление — светлое, системный шрифт, нейтральная боковая панель, синие исходящие и серые входящие сообщения. Все кнопки выполняют реальные действия; индикаторы участников и непрочитанных берутся из БД.

Панель ввода закреплена внутри рабочей области, прокручивается только история. На узком экране боковая панель скрывается; переход в другие города доступен через каталог. Visual Viewport учитывается при изменении доступной высоты, масштабирование страницы не отключается. Поле растёт до 128 px; Enter отправляет с компьютера, Shift+Enter добавляет строку, Ctrl/Command+Enter поддерживается. На сенсорном устройстве обычный Enter остаётся новой строкой.

Действия сообщения находятся в клавиатурно-доступном меню. Настройки, жалоба и подтверждение удаления используют собственные диалоги с возвратом фокуса вместо `window.confirm`/`window.prompt`. Незавершённый черновик восстанавливается после отмены редактирования. Пришедшие сообщения не пересоздают неизменённые DOM-узлы. Собственное сообщение или правка не должны вызывать плашку новых входящих сообщений.

Учитываются reduced motion, reduced transparency и повышенный контраст. Нет декоративных анимаций сообщений; короткая обратная связь на нажатие и открытие панелей отключается при управлении клавиатурой или reduced motion. Меню позиционируется относительно вызвавшей его кнопки.

После обновления нужны collectstatic и обычный перезапуск приложения, новых миграций для редизайна нет. Проверены 46 тестов модуля на PostgreSQL и браузерная работа двух процессов с Redis: переписка, правки, удаления, жалобы, клавиатурное меню, отмена редактирования без потери черновика, размеры от 320 px, низкий viewport, длинный ввод и возвращение фокуса. Это браузерная эмуляция, не физический iPhone.

## Обновление после стабилизации деплоя

34 падения предыдущего полного PostgreSQL-прогона разобраны: часть возникала из-за SQL_ASCII/C в шаблоне локальной тестовой БД, остальные — из-за nullable JOIN при блокировке, владения соединениями рассылок, некорректных тестовых фикстур и читаемости фильтров. Повторный полный прогон на UTF-8 PostgreSQL: 1016 passed, без падений. Три браузерные проверки прошли отдельно. Глобальная проверка миграций теперь чистая; две новые миграции метаданных не выполняют SQL над таблицами. Предыдущие цифры и ограничения выше относятся к раннему этапу работы; актуальные шаги и результаты — в `docs/dokploy-runbook.md`. На рабочий сайт изменения ещё не выпускались.
