## Что изменено в репозитории

1. `requirements.lock`: все runtime-зависимости с точными версиями и SHA256. Docker устанавливает их через `--require-hashes`. Сборка не должна внезапно переходить на новую Django после очередного push. Обновление зависимостей — отдельный проверяемый PR.
2. Python base image закреплён по patch-версии и Debian trixie. Системные пакеты остаются из репозитория Debian; это не побитово воспроизводимый образ.
3. `.dockerignore` исключает `.env.*`, `.passwords`, ключи, локальные окружения, node_modules и временные артефакты.
4. CSS bundle и WhiteNoise manifest собираются внутри образа с фиктивным build-only SECRET_KEY. Продакшн-секреты при сборке не используются.
5. Старый общий том static_data больше не подключается: HTML и хешированная статика относятся к одному релизу. **Сам старый том не удаляется**.
6. `prepare_deployment`: ожидание PostgreSQL ограничено 120 секундами, миграции сериализованы PostgreSQL advisory lock. Ожидание блокировки также ограничено 120 секундами; ожидание DDL-блокировки — 15 секунд. Ошибка миграции останавливает web, а не маскируется.
7. Web и chat работают от пользователя 10001. Cron остаётся root для системного cron daemon; его файл окружения создаётся сразу с правами 0600 без shell-интерпретации значений.
8. `/health/live/` проверяет процесс, `/health/ready/` — БД/кэш, а в chat-контейнере ещё отдельный chat Redis. Пробы не отправляют Telegram и не создают подписки. Отказ chat Redis не выключает весь HTTP-сайт.
9. Chat и cron стартуют только после готовности web. У web/chat есть Docker healthchecks; логи приложения ограничены 3 файлами по 10 MB.
10. Traefik получает явную dokploy-network для web и chat. `/ws/chats/` имеет приоритет 1100, обычные страницы — 1000. БД и Redis наружу не публикуются.
11. Telegram webhook больше не перенастраивается при каждом запуске. После смены домена/токена выполнить отдельно: `docker compose -p tennisfan-site-rthluy -f docker-compose.dokploy.yml exec web python manage.py set_telegram_webhooks` из каталога кода. При TELEGRAM_ENABLED=False оставлять выключенным.

## Уже сделано на сервере без перезапуска сайта

- Установлен `/usr/local/sbin/tennison-backup`.
- `/etc/cron.d/tennison-backup` запускает его ежедневно в **03:17 по Москве**, текущей зоне сервера.
- Резервные копии: `/var/lib/tennison/backups/`, каталог 0700, архивы 0600. Скрипт использует штатный pg_dump 16 из контейнера БД, проверяет архив через pg_restore --list и только затем публикует файл.
- Одновременные backup-запуски блокируются flock. Пароли не передаются в аргументах команд и не записываются в логи. Старые архивы не удаляются и не перезаписываются.
- Права каталога приложения Dokploy ограничены 0700; текущий сгенерированный .env — 0600. Dokploy может снова создать .env с 0644 при следующем выпуске, сейчас закрытый родительский каталог дополнительно защищает его. После обновления самого Dokploy права следует перепроверить.
- Первая копия дополнительно полностью восстановлена в отдельный временный PostgreSQL без сети и без обращения к боевой БД.

**Ограничение:** копии на том же VPS не защищают от потери диска/сервера. Настройте отдельное приватное S3-хранилище для backup. Не используйте публичный бакет медиа и не вставляйте ключи в репозиторий. В Dokploy добавьте S3 destination и backup PostgreSQL Compose-сервиса `db`. Сначала проверьте полное восстановление. Политику удаления старых копий согласовать отдельно; сейчас автоматического удаления нет. Следите за свободным местом.

## Разовая настройка в Dokploy

1. Откройте **tennisfan → site**.
2. Убедитесь: Repository `Skifmail/TennisFan`, Branch `main`, Compose path `docker-compose.dokploy.yml`. Не переключайте проект с Docker Compose на Stack: правила dependencies/labels отличаются.
3. В **Environment** оставьте действующие значения SECRET_KEY, POSTGRES_DB/USER/PASSWORD, ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS. Не генерируйте новый SECRET_KEY при каждом выпуске: он общий для web и chat и подписывает сессии.
4. ALLOWED_HOSTS содержит все четыре домена без схемы; CSRF_TRUSTED_ORIGINS — те же домены с `https://`. Не ставьте `*`.
5. CHAT_REDIS_URL можно не задавать: Compose уже использует `redis://chat_redis:6379/0`. Если задано старое значение, замените его этим внутренним URL. Не используйте кеширующий redis с allkeys-lru для Channels.
6. В **Advanced → Command** укажите полный override (Dokploy добавляет начальное `docker` самостоятельно):

   ```text
   compose -p tennisfan-site-rthluy -f docker-compose.dokploy.yml up -d --build --remove-orphans --wait --wait-timeout 300
   ```

   Это не выполнено автоматически через внутреннюю БД Dokploy: изменение требуется сохранить в интерфейсе/API. `--wait` заставляет выпуск ждать готовности web/chat, а не считать один старт контейнера успехом. Таймаут не откатывает релиз автоматически.
7. В **Domains** оставьте существующие HTTP-домены на сервисе `web`, порт 8000. Новую WS-маршрутизацию задают labels в репозитории; порт 8001 на хосте не открывайте.
8. Проверьте в GitHub **Settings → Webhooks**: нет двух одинаковых активных push webhook для одного Dokploy-сервиса. Не удаляйте GitHub App и чужие интеграции наугад.
9. Перед первым релизом выполните через SSH `/usr/local/sbin/tennison-backup` и убедитесь, что появился новый архив. Ежедневный backup не заменяет backup непосредственно перед опасной миграцией.
10. После сохранения всех изменений в репозитории выполните обычный push в main. Ожидаемый состав: `db`, `redis`, `chat_redis`, `web`, `chat`, `cron`.

Для PostgreSQL уже используются существующие том и имя Compose-проекта. **Не меняйте appName/имя проекта, не выбирайте fresh volumes и не запускайте down -v.**

## Автоматические проверки GitHub

Workflow `.github/workflows/deployment-checks.yml` выполняется на push main и pull request:

- реальный UTF-8 PostgreSQL и **полный** набор `tests/`, включая чат, турнирные сценарии, подписки и запуск;
- mypy strict, Black, Ruff для новых модулей и pip-audit locked runtime;
- два процесса Uvicorn, настоящий Redis и браузерные тесты;
- Stylelint и проверка синтаксиса JS;
- реальная сборка Docker-образа, проверка зависимостей, наличия chat CSS в manifest и отсутствия .env/.passwords.

CI теперь запускает **весь** набор `tests/` и глобальный `makemigrations --check --dry-run`. Проверка test_database_encoding гарантирует UTF-8 и регистронезависимое преобразование кириллицы. В контейнере PostgreSQL явно задаётся `POSTGRES_INITDB_ARGS=--encoding=UTF8`. Перед браузерными тестами Python собирает общий CSS bundle, чтобы не проверять устаревший style.min.css. Не запускайте `makemigrations` автоматически на production: миграции создаются разработчиком и коммитятся в репозиторий.

### Важно: прямой Auto Deploy не ждёт GitHub Actions

По умолчанию нынешний Dokploy начнёт сборку сразу при push, независимо от результата CI. Для настоящего барьера «сначала проверки, затем деплой» нужен единственный источник запуска:

1. Настройте HTTPS-адрес панели Dokploy. Существующий `http://IP:3000` нельзя использовать для отправки API key из GitHub по незащищённой сети. Доступ к панели на время настройки возможен через SSH tunnel: `ssh -N -L 127.0.0.1:13000:127.0.0.1:3000 root@77.222.38.175`, затем открыть `http://127.0.0.1:13000` локально. Такой tunnel подходит для ручного входа, но не заменяет HTTPS endpoint для GitHub Actions.
2. Создайте ограниченный API key в Dokploy. В GitHub **Settings → Secrets and variables → Actions → Secrets** добавьте `DOKPLOY_URL` (HTTPS), `DOKPLOY_API_KEY`, `DOKPLOY_COMPOSE_ID` (ID сервиса site из Dokploy, не appName).
3. **Выключите прямой Auto Deploy в Dokploy**, иначе получится два независимых деплоя.
4. В GitHub Actions Variables задайте `DOKPLOY_DEPLOY_ENABLED=true`. Если используете environment production, настройте его доступы и approvals. Без этого флага workflow не вызывает деплой.
5. Защитите main: изменения только через PR, обязательные jobs **checks** и **image**, актуальная ветка/merge queue. Иначе прямой push может попасть в main без предварительных проверок.
6. Сделайте проверочный PR/push. Последний job `deploy` вызывает официальный `compose.deploy` только после checks/image и пропускает устаревший workflow, если main уже изменился.

Dokploy клонирует текущую ветку, а не SHA артефакта GitHub. Проверка актуальности уменьшает гонку, но не является атомарным закреплением коммита. Для строгой привязки тестируемого и выпускаемого образа нужен отдельный этап публикации образов в registry по SHA и переключение Compose на immutable digest; текущий build-from-Git такой гарантии не даёт.

Без доступа к настройкам GitHub/HTTPS панели эти пункты нельзя считать включёнными. API keys нельзя пересылать обычным сообщением.

## Приёмка после выпуска

Из каталога `/etc/dokploy/compose/tennisfan-site-rthluy/code`:

```bash
docker compose -p tennisfan-site-rthluy -f docker-compose.dokploy.yml ps
# web и chat должны стать healthy; cron должен оставаться запущенным.
docker compose -p tennisfan-site-rthluy -f docker-compose.dokploy.yml exec web python -m scripts.healthcheck 8000
docker compose -p tennisfan-site-rthluy -f docker-compose.dokploy.yml exec chat python -m scripts.healthcheck 8001
curl --fail --silent --show-error https://tennisfan.ru/health/ready/
```

Ожидаемый JSON: `{"status":"ok"}`. Публичный ready проверяет HTTP; отдельная проба chat обязательна. Docker unhealthy сам по себе **не перезапускает** зависший процесс: restart policy срабатывает при выходе процесса. Для автоматического восстановления/оповещений нужен мониторинг, а не только healthcheck.

Под двумя обычными тестовыми аккаунтами:

1. Вступить в один и тот же город, отправить сообщение и ответ. Проверить доставку без обновления страницы, правку и удаление.
2. В инструментах браузера найти `/ws/chats/<id>/`: ответ **101 Switching Protocols**. HTTP 403 для неавторизованного пользователя сам по себе не является полным тестом чата.
3. Перезапустить только chat, убедиться в переподключении и отсутствии дублей; временно отключать боевой Redis ради проверки не нужно.
4. Проверить мобильный интерфейс и существующие разделы/загрузку S3-медиа.
5. Открыть логи web/chat/cron; не копировать окружение и токены в отчёты.

## Откат

- Compose на одном VPS не обеспечивает бесшовный blue-green. При пересоздании web возможна короткая пауза, WebSocket-клиенты переподключаются.
- При ошибке не удалять БД/тома и не обновлять зависимости наугад. Сохранить безопасный фрагмент ошибки, проверить состояние контейнеров и место на диске.
- Если миграция не меняла несовместимо схему, выпустить предыдущий известный Git ref/исправляющий revert через Dokploy. Не переписывать историю main force-push.
- Откат кода не откатывает схему БД. Восстановление дампа поверх боевой базы разрушительно, требует остановки пишущих процессов, отдельного согласования и учёта новых записей после backup.
- Сначала восстановить нужный архив в отдельную БД и проверить его, только затем планировать переключение. Не делать автоматический `migrate <old>` при любой ошибке запуска.
- Новый lock обновлять осознанно: `uv pip compile requirements.txt --python-version 3.12 --generate-hashes --no-annotate --output-file requirements.lock`. Без `--upgrade` uv сохраняет существующие совместимые pins; затем проверить tests/build/security отдельно.

Официальные справочники: [Docker Compose](https://docs.dokploy.com/docs/core/docker-compose), [домены и сети](https://docs.dokploy.com/docs/core/docker-compose/domains), [Auto Deploy](https://docs.dokploy.com/docs/core/auto-deploy), [Compose API](https://docs.dokploy.com/docs/api/compose).

### Разбор 34 падений: завершён

Ранее полный запуск выполнялся на некорректно созданном тестовом PostgreSQL: основной smoke database был UTF8, но **template1 оставался SQL_ASCII/C**. Новые test_* базы наследовали этот шаблон. Боевой сервер проверен read-only: **UTF8 / en_US.utf8**. Для повторных прогонов создан отдельный кластер UTF8/C.UTF-8 на localhost:15433; production и прежний кластер не переинициализировались.

- **19 проверок** прошли без изменения бизнес-кода на корректном UTF-8 кластере. Исчезли ложные превышения VARCHAR для кириллицы и ошибки поиска. Увеличивать лимиты или добавлять фиктивные обходы поиска не потребовалось.
- Блокировка рассылки итогов: `select_for_update(of=("self",))` блокирует турнир, но не nullable-сторону LEFT JOIN клуба. Проверены наличие/отсутствие клуба и конкурентная попытка двух потоков: право на рассылку получает только один.
- Новый `apps/core/db_context.py` управляет соединением трёх фоновых рассылок. Задача не закрывает чужую активную транзакцию; собственное соединение закрывается в finally, включая ошибки. Проверены inline on_commit и настоящий отдельный поток PostgreSQL.
- Три старых unit-теста доступа к Telegram-чату использовали объект без аутентификации и pk, хотя функция теперь получает подписку через ensure_current_subscription. В unit-тесте подменяется только эта зависимость; сохранены все четыре исхода и проверяется её вызов. Добавлены четыре интеграционных случая с реальными подписками: доступ, запрет по тарифу, неактивность, истечение с возвратом на Free и сохранением FT-баланса. Бизнес-правила не менялись.
- В тесте длинного уведомления название турнира превышало разрешённые моделью 200 символов ещё до проверки Notification. Теперь берётся максимальная **допустимая** длина из модели, отдельно доказано, что полный текст всё равно длиннее лимита уведомления, и сохранена проверка сокращения до 255. Ни лимит модели, ни проверка сообщения не ослаблены.
- Панель фильтров спарринга переносит поля с минимумом 16rem на широких экранах. Проверены реальные страницы при 1440, 1100, 900, 390 и 320 px. Дублирующее CSS-правило удалено, эквивалентные записи нормализованы для Stylelint; тема других страниц не переделывалась.
- Добавлены subscriptions.0022 и users.0039, синхронизирующие только метаданные полей с уже существующим кодом. `sqlmigrate` для обеих показывает **no-op**: изменения таблиц, значений и прав подписок отсутствуют. Глобальный `makemigrations --check --dry-run` больше не обнаруживает расхождений.

**Итог:** полный PostgreSQL-прогон — **1016 passed**, 138 успешных subtests, без падений. Браузерные проверки запускаются отдельно на стенде: **3 passed** (два теста чата и новая панель фильтров).
