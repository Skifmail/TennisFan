# Общие журналы web и cron

## Причина ошибки

Несколько независимых процессов Loguru открывали одинаковые активные файлы.
`enqueue=True` сериализует очередь одного обработчика, но не запись и ротацию
между отдельными запусками cron. После переименования файла одним процессом
другой продолжал писать в прежний дескриптор; записи не попадали в активный
журнал или ZIP. Параллельная ротация также могла дать `FileNotFoundError`.

## Исправление

`logging_config.DailyFileSink` использует Linux `fcntl.flock` на общем
`logs/.rotation.lock`. Запись, проверка даты, ротация и очистка выполняются
под одной межпроцессной блокировкой. Активный файл открывается заново для
каждого сообщения; при отсутствии имени создаётся вновь. Дескриптор блокировки
также открывается на каждую операцию, чтобы процессы после `fork` не разделяли
одно открытое файловое описание.

Сохранены `all.log`, `info.log`, `warnings.log`, `errors.log`, пороги уровней,
`enqueue=True`, ротация при первой записи после полуночи, ZIP и срок хранения
7 дней. ZIP сначала полностью создаётся во временном файле. Активные журналы
очистка не удаляет; события очистки записываются после снятия блокировки.
Все процессы, пишущие в один каталог, должны использовать новый обработчик.
Рабочие часы, файлы журналов и старые строки ошибок при выпуске не меняются.

## Регрессионные проверки

```bash
venv/bin/pytest tests/unit/test_logging_cleanup.py tests/unit/test_logging_multiprocess.py --no-cov -q
```

- Второй процесс, открытый до ротации первым, не теряет свою запись.
- Исчезновение имени активного файла не мешает следующей записи.
- Шесть процессов одновременно сохраняют все 180 сообщений без дублей;
  каждый из четырёх журналов ротируется один раз.
- При старте старые архивы удаляются, а активные журналы сохраняются.

Тесты копируют модуль в отдельный временный каталог. Проверку опубликованного
кода также выполнять только в изолированном каталоге, не изменяя production-логи.

## Сопутствующие исправления CI

Nullable-связи в юниорских откликах и неоплаченных турнирных парах больше
не включаются в `FOR UPDATE`: блокируется изменяемая строка через
`of=("self",)`. Транзакции, проверки владельца и защита повторных действий
сохраняются. Файловые тесты читают весь поток штатного Django Client и проверяют
JPEG вместо прямого `response.close()`, закрывавшего тестовую транзакцию.

Новая `notifications.0021_broadcast_audience_database_defaults` добавляет
значения по умолчанию на уровне БД, чтобы INSERT прежней версии приложения
мог не перечислять поля аудитории. Данные рассылок не переписываются;
опубликованная миграция 0020 не меняется. Для отката кода 0021 откатывать
не требуется. Исправление `OneToOneField` и миграция tournaments.0082 сохранены.

Браузерные тесты используют актуальные тексты, ID карточки и точные названия
кнопок. Длинные данные тренировки достигают реальных лимитов модели.
Функциональные проверки, приватность контактов и доступ к WebSocket
постороннего пользователя не отключены.

Для полного локального PostgreSQL-прогона нужна новая тестовая БД или
`--create-db`: `--reuse-db` после транзакционных тестов может повторно открыть
БД, очищенную `flush`, без данных seed-миграций. Это не эквивалент чистого CI.
