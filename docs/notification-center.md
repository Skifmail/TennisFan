## Пользователь

`/notification-center/settings/`: ровно два глобальных переключателя — push и email.
Выбор событий отсутствует. ЛК и история не зависят от этих двух согласий.
Email по умолчанию сохраняет прежнее поведение, персональные push по умолчанию выключены.
Восстановление доступа и подтверждение email — служебные письма, не отключаемые общим
пользовательским переключателем. Администратор видит их отдельными событиями; отключение
их email-канала намеренно прекращает соответствующие письма, поэтому требует осторожности.

Общее согласие push относится к аккаунту, кнопка в футере — к текущему устройству.
Явное включение кнопкой также включает общее согласие аккаунта. Отключение одного
устройства не затрагивает другие. Выключение общего push-переключателя прекращает новые
персональные отправки на все устройства, не отзывает разрешение браузера и не удаляет ЛК.

## Администратор

Отдельный раздел Django Admin «Уведомления»:

- «События и каналы»: строки событий, столбцы Email / Push / ЛК, поиск и фильтры;
  несколько чекбоксов можно сохранить одним действием. Django LogEntry хранит изменения.
- «Ручные рассылки»: заголовок до 40 символов, текст до 120, опциональный переход
  только на HTTPS-страницу платформы без секретных параметров. Короткий текст одинаков
  для выбранных каналов; это не редактор длинных HTML-писем.
- Два ограничения формы дублируются серверной проверкой. Счётчики показываются в форме.
  Ограничение длины не гарантирует полное отображение на любом экране.
- Сначала сохранить черновик, затем «Предпросмотр и подтверждение». Здесь видны текст,
  каналы и оценка числа пользователей (у одного пользователя бывает несколько устройств).
- «Тест только мне» создаёт отдельную копию, адресованную исключительно текущему
  администратору. Его собственные согласия и разрешения устройств учитываются.
- Массовый POST требует отдельного `notifications.send_broadcast`, CSRF и подписанного
  снимка содержимого со сроком 5 минут. Подтверждённое содержимое блокируется от изменений.
- Повторное подтверждение того же черновика не создаёт новую рассылку. Аудитория ограничена
  верхним user_id на момент подтверждения; зарегистрированные позже не включаются.
- «Журнал доставки», «Push-устройства», «Согласия пользователей» доступны только для
  наблюдения: администратор не подменяет пользовательские согласия.
- «Остановить очередь рассылки» требует отдельного подтверждения и права отправки.
  Остановка исключает последующие задания, но не отзывает уже принятые или выполняемые
  сообщения. Старый раздел записей ЛК оставлен только для просмотра истории: ручные
  отправки выполняются через центр, без обхода политики каналов.

Email-получатели — активные пользователи с разрешением email. Push — с явным общим
согласием и активными привязанными устройствами. Для ЛК пользовательских отказов нет.
Разрешения события проверяются при формировании и ещё раз перед внешней отправкой.
Существующие бизнес-правила адресации, город, членство, права и старые ограничения
клубного email не расширяются автоматически.

## Полнота событий и исключение дублей

`apps/notifications/domain/catalog.py` содержит явные коды, русские названия,
группы и связи с существующими производителями. Полный перечень — в
[инвентаризации](notification-event-inventory.md). Коды не распознаются по тексту письма.

Для события, уже создающего ЛК, именно новая запись ЛК является источником push;
его email-дубль только применяет почтовую политику. Для события, существовавшего только
в почте, адаптер фиксирует нейтральную запись и push независимо от общего отказа от email.
Для событий, ранее существовавших только в ЛК, разрешённый email создаётся через очередь.
Таким образом чекбоксы доступны и для новых каналов, а не только для старых отправок.
Тексты подтверждения/восстановления с токенами не копируются в push или ЛК.

AST-тест инвентаризации запрещает новые прямые `Notification.objects.create` и отправители
без event_key вне самого центра. Для нового бизнес-события нужно добавить реестр,
политику миграцией, явный адаптер и тест получателей. Исторические записи не переигрываются.

При выключении ЛК у события новая техническая запись получает `is_visible=False`: она
нужна для существующих FK приглашений и не показывается в ленте или счётчике. Старые записи
сохраняют видимость. Это не удаление пользовательской истории.

## Очередь и ограничения гарантий

`process_notifications` выполняется существующим cron раз в минуту. Массовая рассылка
разворачивается пакетами по 100 пользователей. Вызов worker ограничен 100 доставками.
Сетевой транспорт не выполняется в пользовательском HTTP-запросе ручной рассылки.

Задания push атомарны с созданием ЛК; откат транзакции не оставляет задачу.
Worker использует блокировку/аренду, повторную проверку согласия, состояния аккаунта,
срока задания и действующих устройств. Push повторяется ограниченно с тем же UUID
идемпотентности; недоступные подписки и постоянные ошибки не повторяются автоматически.
SMTP не имеет надёжной идемпотентности: после прерывания worker или неоднозначной ошибки
ставится `uncertain`, а не повторное письмо вслепую. Ошибки не меняют бизнес-объекты.
Неизвестное событие или отсутствующая строка политики закрывают только одно задание
с `failed`, а не останавливают весь пакет. Прерванное email-задание закрывается
как `uncertain` до разбора следующих заданий.

`accepted` означает принятие OneSignal/SMTP, **не гарантированную доставку или прочтение**.
Если OneSignal вернул `recipients=0` или пустой `id`, задание получает
`failed`/`push_no_recipients`, а использованные подписки деактивируются, чтобы не
тратить следующие задания на мёртвые адреса; повторная привязка выполняется явно.
Система исключает повторы одного задания и дублирование push из двух
старых каналов, но не обещает exactly-once для SMTP или повторно вызванного
бизнес-действия, которое само создаёт новое событие.

### Браузеры и мобильный Яндекс

На iPhone и iPad web push работает только из приложения, добавленного на экран
«Домой». В обычной вкладке, в том числе в Яндекс Браузере, кнопка подключения
скрывается, а вместо неё показывается инструкция: это не неисправность сайта.
Для установки есть пошаговая инструкция с картинками: Safari → «Поделиться» →
«Показать больше» → «Добавить на экран „Домой“» → включить «Открыть как
веб-приложение» → «Добавить». Контакты на скриншотах размыты, изображения
открываются полностью по нажатию.

На Android Яндекс Браузер получает SDK OneSignal напрямую, минуя проверку
загрузчика, которая может ложно считать мобильный браузер неподдерживаемым.
Если уведомления запрещены в настройках сайта или телефона, кнопка остаётся
доступной и предлагает «Проверить снова» вместе с точной инструкцией. Если SDK
не загрузился, показывается «Повторить», а не постоянно неактивная кнопка.
Под кнопкой есть раскрывающаяся инструкция для Android: отдельно для Яндекс
Браузера и Google Chrome, включая проверку системного разрешения на уведомления.
Путь Яндекса: ⋮ → «Настройки» → «Уведомления» → «Уведомления от сайтов»;
дополнительно рекомендуется снять ограничения батареи для браузера.
OneSignal перечисляет браузеры, которые получают push при закрытых окнах
(Chrome, Firefox, Opera, Edge), и Яндекс Браузера в этом списке нет. Поэтому для
надёжных фоновых уведомлений на Android используйте Chrome или установите сайт
на главный экран; Яндекс Браузер показывает push, пока его процесс жив.

После подтверждения устройства в настройках доступна кнопка «Проверить доставку».
Она отправляет тестовый push только на подтверждённую подписку текущего
пользователя, не чаще одного раза в 30 секунд. Ответ `accepted` снова означает
только приём сообщения OneSignal: если push не появился, нужно проверить
разрешения сайта, системные уведомления и фоновые ограничения Android.

Кнопка проверяет только прямое подключение из web-процесса. Рабочие события идут
другим путём — через очередь `Delivery` и cron-контейнер, поэтому «тестовый
приходит, рабочий нет» почти всегда означает различие в одном из этих звеньев:

- `notification_push_probe --email <email> --check-provider` ставит пробное
  задание в ту же очередь, ждёт решения worker и печатает статус, `provider_id`
  и счётчики OneSignal. Команда проходит тот же путь, что и рабочие события,
  и не создаёт запись в ЛК. Ненулевой код возврата означает, что worker не принял
  задание: смотрите `--wait`, журнал cron и `notification_queue_status`.
- `notification_delivery_report --email <email> --limit 10 --check-provider`
  показывает подписки устройства, последние задания и статистику доставки.
  Сравните `subscription_id` из отчёта с подпиской в кабинете OneSignal:
  `successful=0` указывает на таргетинг, `successful>0` — на устройство и браузер.
- Команды нужно уметь запускать и в `web`, и в `cron`: отсутствие команды в cron
  означает, что контейнер работает на старом образе. Push из старого образа
  собирается по другому таргетингу, поэтому сверяйте версии.

Срок жизни push у провайдера — 12 часов, срок задания в очереди — сутки. Это
нужно для мобильных браузеров без постоянного фонового процесса: если браузер
был закрыт, OneSignal хранит сообщение и показывает его при следующем открытии,
пока не истёк `ttl`. Час хранения для такого сценария слишком мал: push,
отправленный вечером, не доживал до утра.

Сайт отвечает на `https://tennisfan.ru`. Запросы к `www.tennisfan.ru`
перенаправляются туда же кодом 308 с сохранением пути и query, поэтому браузер
не создаёт подписку на origin, который не разрешён в OneSignal. `www.tennistop.ru`
перенаправляется на `https://tennistop.ru`; TennisTop остаётся отдельным брендом,
и web push на нём не включены.

### Наблюдение и ретенция

- `notification_queue_status --max-age-minutes 15` показывает счётчики `queued`,
  `due`, `scheduled`, `processing`, `stuck`, `stale_email` и завершается с ненулевым
  кодом при отставании. Cron вызывает команду каждые 5 минут; вывод остаётся в журнале
  контейнера.
- `cleanup_notification_history` ежедневно удаляет только завершённые задания старше
  30 дней, истёкшие коды подтверждения и неактивные/истёкшие устройства. Перед
  удалением устройств команда отзывает их подписки у провайдера; `--dry-run`
  показывает объём и не делает сетевых запросов. История ЛК и подтверждённые
  рассылки не удаляются.
- `/health/notifications/` возвращает 200 при разобранной очереди и 503, если
  просроченное задание ждёт дольше 15 минут или обработка зависла. Это отдельная
  проба для внешнего мониторинга: она не участвует в healthcheck контейнера, чтобы
  отставание cron не перезапускало web-процесс. Остановленный cron виден только
  внешней пробе, а не `/health/ready/`.

### Чаты: присутствие и мгновенные push

Для `chat.direct_message` и `chat.reply` push создаётся сразу после сообщения,
если получатель не открыл эту комнату. Сообщения не склеиваются и не ждут окна:
каждое новое сообщение или ответ даёт отдельное задание. В тексте нет переписки
и имён; в ЛК по-прежнему сохраняется каждое уведомление.

Присутствие хранится в общем кэше (Redis в production) с heartbeat каждые 25 секунд
и TTL 120 секунд. Пока у получателя открыта WebSocket-комната, новое push-задание
не создаётся. При открытии комнаты уже стоящее в очереди задание помечается
`seen_in_chat`; worker повторно проверяет присутствие перед отправкой. Если кэш
недоступен, push отправляется, чтобы не терять уведомление.


## Защищённая персональная адресация

Нельзя рассылать персональные события через Total Subscriptions или доверять одному
присланному браузером ID. JWT Identity Verification для Web SDK не поддерживается:
**не включать Identity Verification и не создавать P-256 ключ для сайта**.

Сервер создаёт случайный HttpOnly Secure cookie и поколение привязки. Нажатие
«Включить» отправляет на конкретный `include_subscription_ids` одноразовый код
в ссылке общего push без данных аккаунта. Код хранится только в виде SHA-256,
действует 5 минут и отсутствует в JSON ответе браузеру. Частота: не чаще раза в минуту
на браузер/подписку и не более пяти разных браузеров аккаунта за минуту.

Открытие ссылки показывает отдельную страницу без сторонних ресурсов с no-store,
no-referrer и строгой CSP. GET ничего не активирует. Явный POST с CSRF, тем же cookie,
аккаунтом и поколением атомарно потребляет код и включает подписку. Чужой браузер,
истёкший или повторный код, выход и смена аккаунта отклоняются. Выход отзывает адрес
до любых SDK callback. После выхода/повторного входа потребуется новое подтверждение.
Старая вкладка не активирует отозванное поколение. Смена ID подписки требует нового кода.

Отзыв устройства — единая точка `revoke_devices()`: локальная запись становится
неактивной, `subscription_id` очищается, а сама подписка удаляется у провайдера
(`DELETE /apps/{app_id}/subscriptions/{id}`). Так удалённое из базы устройство не
остаётся живым адресом в OneSignal, куда продолжали бы уходить уведомления. Отказ
или сетевой сбой провайдера не отменяет локальный отзыв: подписка уже не выбирается
для отправки, а провайдер удалит её позже. Повторное удаление безопасно — `404`
считается достигнутой целью, а браузер может подписаться заново и подтвердить
устройство новым кодом. OneSignal сам подписки не удаляет: на платном плане хранит
бессрочно, на бесплатном чистит только через 18 месяцев неактивности.

Адрес подписки уникален; подтверждённый перенос отзывает старого владельца. Worker
отправляет только конкретным подтверждённым subscription IDs, никогда alias или сегменту.
Неподтверждённые старые строки устройств не адресуются. История ЛК не изменяется.
Срок привязки продлевается до срока текущей сессии при **любой** авторизованной
активности, а не только при открытии страницы уведомлений. Запись обновляется
не чаще раза в час на устройство. Если пользователь запретил уведомления в ОС,
браузер при следующей синхронизации отзывает серверную привязку; это уменьшает
число мёртвых адресов, но не заменяет проверку `recipients` провайдера.
SDK `login`/`logout` не используются. Код находится во фрагменте ссылки (`#code`),
который не отправляется в HTTP GET и access-логи. Локальный скрипт удаляет фрагмент из адресной строки и передаёт код
только в теле подтверждающего POST. Страница не загружает сторонние ресурсы.

При включённом центре тяжёлый SDK OneSignal подключается только на странице
уведомлений, где есть кнопка подписки. В legacy-режиме он остаётся на страницах с
общим блоком управления. Манифест PWA и обработчик клика по push остаются на всех
страницах, поэтому установка приложения и переход из уведомления не зависят от
визита в настройки.

Ссылки в push и ручных рассылках могут содержать обычные query-параметры
(`?type=tournament&id=42`, страницы, фильтры), чтобы переход вёл на конкретный объект.
Фрагменты и параметры с токенами, кодами, подписями, сессиями и email запрещены:
такая ссылка уходит OneSignal. Слишком длинные ссылки (более 255 символов) отвергаются.

Публичная форма восстановления пароля ограничена пятью запросами за 15 минут
на IP и отдельно на адрес. При превышении возвращается тот же редирект, что и при
успехе, поэтому лимит не раскрывает наличие аккаунта.


## Подключение в отдельном релизе

1. Сохранить свежий бэкап БД, текущие образы и параметры отката.
2. Применить миграции с флагом центра **False**. Проверить старые письма, ЛК, приглашения,
   сайт и чат. Миграции добавляют таблицы/поля, историю не очищают.
3. **Не включать Identity Verification**. Настроить только серверный
   `ONESIGNAL_REST_API_KEY` через защищённое соединение. Не публиковать ключ в Git,
   JS, скриншотах или логах. Для стенда использовать отдельный проект.
4. После отдельного подтверждения включить `NOTIFICATION_CENTER_ENABLED=True` в web/chat/cron.
   Проверить `/notification-center/identity/`, затем нажать «Включить», открыть push
   и подтвердить подключение на отдельной странице. Старые анонимные подписки сами
   не включают персональный канал. Миграция 0003 добавляет проверенные адреса и коды.
5. Сначала включить push только своим тестовым аккаунтам. Проверить iPhone и Chrome:
   личный тест, переход, выход/смену аккаунта, два устройства, общие отказы и сохранение ЛК.
6. Проверить каждую группу событий на тестовых данных: правильный адресат, один push,
   настройки администратора, отсутствие утечки секретов и влияние отказа почты.
7. Реальную массовую рассылку не выполнять без отдельного согласования содержимого,
   аудитории и времени. Для отключения новой очереди вернуть флаг False; уже принятые
   внешним провайдером сообщения это не отзывает. Изменённые чекбоксы центра при этом не
   применяются к старому механизму email: аварийную остановку рассылок планировать отдельно.

## Единая пользовательская панель

Настройки доступны постоянно через меню имени пользователя → «Уведомления» →
«Настроить уведомления». Старый адрес настроек перенаправляет сюда и раскрывает
панель. Два переключателя управляют push для аккаунта и email; отдельная кнопка
подключает или отключает текущее устройство. Перед отключением показывается
предупреждение: история и уведомления ЛК сохраняются, email не меняется.

Приглашение на главной управляется отдельным `NOTIFICATION_PROMPT_ENABLED=False`.
Включать его следует после приёмки перехода из push на реальном iPhone с открытой
и закрытой PWA. «Позже» показывает путь к настройкам и закрывает только текущее
окно; следующая загрузка главной снова предлагает подключение. Явный отказ от
push в настройках аккаунта уважается. Подключение другого устройства не скрывает
приглашение на текущем.

Переход подтверждения на iOS сначала передаёт точную одноразовую ссылку странице
и ждёт подтверждения приёма. Если страница не ответила, проверяется результат
нативного перехода, затем используется открытие окна. Обход ограничен адресом
подтверждения: обычные уведомления и Chrome остаются под управлением OneSignal.
Автоматические проверки имитируют отказ и бездействие нативного перехода;
они не заменяют проверку клика на физическом iPhone.

Поздняя загрузка состояния SDK не считается отказом от push. Фоновая проверка
отправляет состояние только при готовой активной подписке; отзыв устройства
выполняется отдельным явным действием пользователя. Экран обновляется после
завершения проверки. При отказе отправки подтверждения сервер возвращает
`Retry-After`, а интерфейс показывает ограниченное ожидание и допускает ручной
повтор без повторного optIn уже подписанного SDK. Признак Subscribed у OneSignal
не заменяет проверку принадлежности устройства аккаунту TennisFan.

## Восстановление нажатой ссылки в iOS PWA

Результат `postMessage` не считается доказательством загрузки формы. После
`notificationclick` сохраняется единственная точная ссылка подтверждения в
отдельной IndexedDB текущего origin. Получение push само по себе ничего не
сохраняет и не активирует устройство. Код логически действителен не более пяти
минут; сервер независимо проверяет свой срок, cookie, аккаунт, поколение и CSRF.
Ссылка удаляется после фактической загрузки страницы подтверждения либо при
чтении просроченной записи. Смена только fragment старой формы вызывает полную
загрузку документа, иначе можно остаться на уже использованной странице.

Пока явно запрошенное подтверждение ожидается, видимая авторизованная PWA
проверяет локальную передачу раз в секунду, не выполняя сетевых опросов. При
возврате/повторном открытии приложение также проверяет уже нажатую ссылку.
Фоновый, просроченный или гостевой экран не запускает автоматические переходы.
Операции хранилища и нативные операции окон ограничены по времени; зависший
focus не блокирует переход. При недоступной IndexedDB сохраняется предыдущий
путь через сообщения и нативное открытие окна. Chrome и обычные сообщения не
перехватываются этим iOS-обходом.

Признак OneSignal Subscribed означает разрешённый транспорт. Интерфейс отдельно
предлагает «Подтвердить подключение», пока устройство не доказало получение
одноразового кода в исходной авторизованной сессии.

Ожидание нажатой ссылки начинается перед явным запросом подтверждения, а не
после HTTP 202: push может прийти быстрее ответа API либо при потере ответа.
Проверенное активное устройство завершает локальное ожидание без нового кода.
