## 0. Проверить согласованную замену ASGI-сервера

Twisted 26.4.0 отмечен аудитором как уязвимый; готовой исправленной версии на момент проверки нет.
Согласованный вариант: заменить Daphne на Uvicorn, убрать
Twisted из runtime-зависимостей, согласовать команды запуска в обеих Compose-конфигурациях,
Procfile и CI. Бизнес-логику и маршруты чатов не менять.

Сначала написать регрессионные проверки, затем изменить зависимости и запуск.
Зафиксировать версии и хеши без массового обновления остальных пакетов.
Проверить особенности ASGI: lifespan, WebSocket ping/timeout, доверенные proxy headers,
origin validation, авторизацию, отказ Redis, отключение и переподключение клиента.
Учесть, что импорт channels.testing может подтягивать Daphne через live-server helpers;
не маскировать эту зависимость и не объявлять чистую среду проверенной по старому venv.
Проверить чистую установку, pip check, полный аудит без исключений, тесты и два
реальных ASGI-процесса с Redis. До завершения этого пункта выпуск заблокирован.

## 1. Установить фактический способ доставки

Открыть Dokploy → проект tennisfan → site и проверить источник, ветку,
Compose path и Auto Deploy. Названия взяты из старого runbook и требуют подтверждения.
Не нажимать Deploy и не отправлять main: push может немедленно запустить публикацию.
Скриншот не должен содержать ключей и переменных окружения.

## 2. Исключить преждевременную публикацию

По подтверждённой схеме отключить прямой Auto Deploy либо проверить действующий CI gate.
Не включать второй триггер параллельно с первым. Зафиксировать исходное состояние.
Для дальнейшего push отдельно согласовать ветку и момент отправки.

## 3. Зафиксировать состав релиза и пройти CI

Проверить весь diff, включая изменения, сделанные ранее: нельзя автоматически считать
их все частью пуш-уведомлений. Согласовать состав релиза и создать проверяемый commit.
Запустить CI в безопасной ветке без публикации. Требуются зелёные checks и image:
аудит, PostgreSQL/Redis, браузерные сценарии, типы/стиль, реальная Docker-сборка.
Проверить именно согласованный SHA. Локальная сборка статики не заменяет Docker build.

## 4. Подготовить возврат и свежую резервную копию

Записать текущий production SHA/образ и доступный способ его повторного выпуска.
Проверить доступность прежнего образа: повторная сборка старого исходного кода не
гарантирует идентичный образ. Если его нет, подготовить проверенный rollback до выпуска.
По подтверждённому runbook выполнить штатный backup и проверить успешное завершение,
дату, ненулевой размер и журнал проверки архива. Это не равно проверенному восстановлению;
результат последней проверки восстановления фиксировать отдельно.
Не удалять старые копии, тома, БД и медиа; не менять project name.

## 5. Проверить настройки, затем получить разрешение на выпуск

OneSignal: Web / Custom Code, Site URL https://tennisfan.ru, стандартный worker в корне.
Сопоставить ONESIGNAL_SITE_ORIGIN с этим адресом; App ID публичный, REST API key не нужен.
Существующие SECRET_KEY, S3, DB и Telegram настройки не менять и не присылать в чат.
Отдельно подтвердить окно выпуска и согласованный SHA; только затем запускать deployment.

## 6. Проверить выпуск без рассылки

Проверить deployment logs, фактически запущенный SHA/образ и health web/chat/cron/Redis.
Проверить публичные /health/live/ и /health/ready/, вход, страницу турниров и чат двух
участников, в том числе переподключение. Не считать сообщение Dokploy об успехе приёмкой.
Проверить HTTPS, /OneSignalSDKWorker.js (200, JavaScript, без редиректа/авторизации),
/manifest.webmanifest и существование иконки/хешированной статики.
Проверить отсутствие ошибок SDK и регистрации worker, отсутствие автоматического запроса
разрешения и нежелательной загрузки SDK на альтернативных origin.

## 7. Проверить подписку на физических устройствах

Сначала Android / Chrome вне инкогнито: включить подписку кнопкой сайта.
Затем iPhone с iOS 16.4+: добавить сайт на экран Домой через Safari,
запустить с иконки, включить уведомления. Проверить оба устройства в OneSignal как Subscribed.
Добавить их в Test Users, перепроверив получателей перед любой отправкой.

## 8. Отправить только тестовый push

Получить отдельное подтверждение получателей. Отправить тест только двум выбранным
тестовым устройствам, не всей аудитории. Проверить доставку при закрытом сайте и переход
на заданную страницу. Затем проверить выключение/повторное включение и отказ разрешения.
Анонимные подписки привязаны к браузеру, не к аккаунту; личные уведомления не отправлять.

## 9. Зафиксировать приёмку или откат

Записать SHA, время выпуска, результаты Android/iPhone и наблюдения по ошибкам.
Если ухудшились вход, чат, health или начались серверные ошибки — остановить проверку
и выполнить согласованный rollback на предыдущий образ, без удаления томов и БД.
Не откатывать миграции и не восстанавливать БД поверх рабочей без отдельной оценки:
в релиз могут попасть более ранние изменения, а после backup уже могли появиться новые данные.

Если проблема только в новом UI/SDK, аварийный выключатель ONESIGNAL_APP_ID= с
перезапуском отключает его загрузку и новые подписки, но НЕ отзывает прежние разрешения
и НЕ останавливает отправки из кабинета OneSignal. Рассылки прекращать отдельно.
