# Выпуск исправлений Telegram-бота

План для изменений от 6 ноября 2026. Это инструкция оператору, **не отметка
о выполненном production-деплое**. `apps/camps/` в исправления не входит.

## Перед выпуском

1. Проверить итоговый diff и полный `tests/` на PostgreSQL и SQLite.
   Конкурентные блокировки принимаются только по PostgreSQL, не SQLite.
2. Проверить `makemigrations --check --dry-run`, Django check, Black, Ruff
   и строгую типизацию выбранных модулей. Глобальная типизация старого проекта
   этим не подразумевается.
3. Сделать свежий приватный backup БД и проверить восстановление отдельно.
   Legacy-миграционный тест использует синтетические данные, не production-копию.
4. Сохранить известный рабочий ref/образ. Не менять имя Compose-проекта,
   тома, `SECRET_KEY`, ключи S3 или настройки БД ради выпуска.
5. Приватно настроить пользовательский токен, явный username, случайный
   webhook-secret и HTTPS-origin. Если настроен исходящий админский бот,
   это должен быть **другой** бот, а не другой токен того же bot ID.
   До сетевой приёмки оставить `TELEGRAM_ENABLED=False`,
   `TELEGRAM_PRIVATE_CHAT_ACCESS_ENABLED=False`.

Одинаковое окружение требуется всем процессам приложения. В Dokploy значения
задаются в Environment и передаются через `x-app-env`; после их изменения
нужна замена процессов, а не только правка `.env` на диске.

### Требования к тестовому стенду

- PostgreSQL проверять на отдельной **свежей** тестовой БД с seed-данными
  миграций. После транзакционных тестов `flush` может удалить реестр
  `EventPolicy`, географию и служебного bye-игрока. Повторный `--reuse-db`
  такой базы не восстанавливает выполненные data-миграции и не годится
  для итоговой приёмки. Не очищать и не пересоздавать рабочую БД приложения.
- Кодировка должна быть `UTF8`, а локаль — поддерживать регистр кириллицы.
  Одного `--encoding=UTF8` недостаточно: локаль `C` оставляет `МОСКВА`
  в нижнем регистре неизменной. На тестовом PostgreSQL проверить:

  ```sql
  SHOW server_encoding;
  SELECT lower('МОСКВА'), upper('москва'), length('Москва');
  ```

  Ожидаются `UTF8` и `москва`, `МОСКВА`, `6`. Например, подходит доступная
  на локальном стенде `ru_RU.utf8`; выбрать совместимую локаль своего образа.
- Параллельные прогоны используют разные БД и файловые хранилища:
  `MEDIA_ROOT`, `JUNIOR_PRIVATE_MEDIA_ROOT`, `SUPPORT_PRIVATE_MEDIA_ROOT`.
  Локальные проверки выполняются с `TELEGRAM_ENABLED=False`, locmem-почтой
  и `-p tests.support.no_external_network`; внешние сценарии принимаются отдельно.

## Переключение и миграции

**Не смешивать старые и новые пишущие процессы.** Старый notification worker
не знает канал `telegram`, а старые игровые сервисы не заполняют `applied_at`.
Обычный независимый rolling update web/cron здесь небезопасен.

1. На время переключения закрыть изменяющие игровые запросы сайта и бота
   на прокси/страницей обслуживания. Для Telegram возвращать технический 503,
   чтобы update не потерялись. Остановить прежний cron и исключить фоновые
   пишущие процессы старого билда. Один `TELEGRAM_ENABLED=False` не заменяет
   остановку всех старых игровых записей.
2. Применить миграции **новым** билдом. В Dokploy это делает сервис `release`
   через `prepare_deployment`; нельзя запускать вторую несогласованную миграцию.
   На отдельном стенде без этого сервиса:

   ```bash
   venv/bin/python manage.py migrate --plan
   venv/bin/python manage.py migrate --noinput
   ```

3. Запустить web/chat/cron только одного нового ref и проверить готовность.
   Снять запрет игровых записей после согласованного переключения всех процессов.

Новые миграции:

- `notifications.0016_telegram_delivery_queue` — Telegram-payload и связь рассылки.
- `telegram_bot.0003_telegram_delivery_queue` — состояние отправителя,
  подготовка рассылок и объявлений турниров.
- `notifications.0017_telegram_delivery_queue` — канал `telegram`, объявления
  и уникальность адресатов пакета.
- `telegram_bot.0004_legacy_broadcast_status` — старые `sent_at` помечаются
  `legacy`, без повторной отправки и без утверждения о подтверждённой доставке.
- `telegram_bot.0005_telegram_update_receipt` — уникальные обработанные update.
- `tournaments.0070_matchresultproposal_applied_at` — отметка применения результата.
- `tournaments.0071_mark_legacy_applied_proposals` — старые принятые заявки
  с пустой отметкой помечаются временем миграции пакетами по 1000.
  Существующая дата, pending и rejected сохраняются; рейтинг не пересчитывается.

Django сам выбирает порядок по зависимостям. Не применять только миграции
одного приложения вручную. Новая схема сохраняет старые push/email-задания,
рассылки и черновики; `legacy` не превращается в новую очередь.

## Проверка без сети

В новом окружении:

```bash
venv/bin/python manage.py check --deploy
venv/bin/python manage.py makemigrations --check --dry-run
venv/bin/python manage.py showmigrations notifications telegram_bot tournaments
venv/bin/python manage.py set_telegram_webhooks --dry-run
```

В контейнере заменить `venv/bin/python` на `python`, например:

```bash
docker compose -p tennisfan-site-rthluy -f docker-compose.dokploy.yml exec web python manage.py set_telegram_webhooks --dry-run
```

Проверка webhook должна показать план для пользовательского бота, а не
«токен не задан, пропуск». Секрет не выводится. Отсутствие настроек закрытого
чата допустимо, пока его флаг выключен. Проверить `cron`: `process_notifications`
есть каждую минуту, `sync_private_chat_access` — каждые 30 минут.

## Сетевая приёмка

Этот этап требует настоящих ботов и отдельного разрешения на их использование.
Локальная успешная проверка не заменяет его.

1. Проверить `getMe` для каждой настроенной роли: bot ID различаются,
   username пользовательского бота соответствует окружению. Не помещать URL
   с токеном, тело update и секреты в логи/отчёт.
2. Включить `TELEGRAM_ENABLED=True` согласованно в процессах и отдельно выполнить
   `set_telegram_webhooks`. `getWebhookInfo` должен показать действующий HTTPS URL,
   нужные `allowed_updates` и отсутствие продолжающейся ошибки. Команда сохраняет
   ожидающие update и удаляет webhook только исходящего админского бота.
3. Двумя обычными тестовыми аккаунтами проверить привязку, меню и личный матч.
   Просроченный/повторный токен не привязывает аккаунт. Старые support-команды
   и `/telegram/support-webhook/` не используются.
4. Внести результат с сайта и бота в **разных** тестовых матчах. Проверить счёт,
   перспективу обеих сторон, однократные рейтинг/FANcoin, ЛК и Telegram-задания.
   Для парного/командного спарринга проверить всех четырёх участников,
   дружеский режим и неизменность состава после создания матчей.
5. Дождаться cron: `accepted` требует provider `message_id`. Повторный запуск
   worker не дублирует сообщение. Рассылка не получает `sent_at` заранее.
   Не держать отключённую сеть больше срока жизни нужных заданий — 24 часа.
6. Нажать «⚠️ Оспорить результат»: после входа `/support/` содержит номер,
   счёт, ссылку и причину. Обращение видно сотруднику; результат сам не отменяется.
7. Проверить продление, неявку и административное исправление на специально
   созданных матчах. Повтор неизменённого ручного результата не создаёт писем
   и не пересчитывает статистику.

### Закрытый чат — отдельный этап

Открытая ссылка должна работать независимо от подписки. Закрытый флаг включать
только после задания двух **разных отрицательных** public/private ID и проверки
прав бота на приглашения, заявки и удаление.

- Действующий подписчик с `has_private_chat=True` получает короткую ссылку
  с заявкой и допускается после свежей проверки.
- Другой аккаунт по пересланной ссылке, неактивный пользователь, истёкшая
  подписка или тариф без права не допускаются.
- `sync_private_chat_access --dry-run` читает Telegram API, но не удаляет.
  Администраторы, создатель и неизвестный статус не становятся кандидатами
  на удаление. После просмотра запускать обычную синхронизацию по согласованию.
- Проверка доступа не переводит подписку на Free и не меняет FANcoin.

## Наблюдение

Проверять возраст и число `queued`, `processing`, `failed`, `skipped`,
`uncertain`; для Telegram смотреть записи `Delivery(channel="telegram")`,
а не только общие показатели push/email. После 429 общая пауза в
`TelegramDeliveryState` сохраняется при перезапуске. `uncertain` требует
ручного разбора: сначала проверить фактическую доставку, не сбрасывать статус
ради слепой повторной отправки. Receipt содержит ID update, а не его текст.

## Безопасный откат

- При сетевой проблеме сначала выключить `TELEGRAM_ENABLED` и/или закрытый
  флаг; очереди, receipt, отметки результата и историю не очищать.
  Если повреждается игровое состояние, ограничить записи до разбора.
- Откатывать код только на проверенный **совместимый** билд. Старый worker
  нельзя запускать поверх новой Telegram-очереди; старый игровой сервис
  не поддерживает защиту `applied_at`. При отсутствии совместимого билда
  оставить ограничения и исправлять вперёд.
- Не выполнять автоматически `migrate <old>`, удаление `Delivery`/receipt,
  сброс `applied_at`, `drop_pending_updates=True` или `down -v`.
  Обратный no-op data-миграций не восстанавливает старую бизнес-семантику.
- Восстановление backup поверх production — отдельная разрушительная операция:
  требует остановки записей, согласования и учёта данных после backup.
